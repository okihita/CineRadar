# Plan: Movie Collection Audit and Consolidation

## Objective
Audit the `movies` collection in Firestore to identify and merge documents that use `schedule_id` (incorrect) as their document ID into their `metadata_id` (correct) counterparts.

## Context & Problem Statement
The TIX.id API uses a dual-ID system:
1.  **`schedule_id` (or `id`)**: A transient ID that changes when a movie moves between cinema chains.
2.  **`metadata_id` (or `movie_id`)**: A stable, immutable identifier for the movie entity.

In the current Firestore `movies` collection:
*   Some documents are correctly indexed by `metadata_id`.
*   Others were incorrectly indexed by `schedule_id`.
*   This causes "Movie metadata not found" errors in the Admin V2 interface, which expects documents to be keyed by `metadata_id`.

## Audit Strategy

### 1. Identifying Problematic Documents
A document is "problematic" if its Firestore document ID (the key) does not match the `movie_id` field within its data payload.

*   **Criteria**: `doc.id != doc.get('movie_id')`
*   **Correct Documents**: `doc.id == doc.get('movie_id')`

### 2. Impact Assessment
*   **Admin UI**: Pages like `/performances_v2/[metadataId]` and `/movies/[id]` will fail to load details if the metadata is keyed by `schedule_id`.
*   **Data Fragmentation**: Rating history might be split between two documents (one with `schedule_id` and one with `metadata_id`).
*   **Duplicate Storage**: We might have multiple documents for the same movie.

## Proposed Implementation Steps

### Phase 1: Audit & Discovery
1.  **Develop an Audit Script**:
    *   Iterate through all documents in the `movies` collection.
    *   Categorize documents into:
        *   `stable`: Doc ID matches `movie_id`.
        *   `mismatched`: Doc ID matches `id` (schedule ID) but not `movie_id`.
        *   `ambiguous`: Doc ID matches neither (rare).
    *   Log all `mismatched` IDs for the merge phase.

### Phase 2: Merge & Migration
1.  **Develop a Merge Script**:
    *   For each `mismatched` document:
        1.  Identify its `metadata_id` (from the `movie_id` field).
        2.  Check if a document already exists with `metadata_id`.
        3.  **Merge Data**:
            *   If `metadata_id` doc doesn't exist: Create it with the data from the `schedule_id` doc.
            *   If `metadata_id` doc exists: Merge fields (preferring the one with more complete data or the latest `scraped_at`).
        4.  **Merge Subcollections**:
            *   Copy all documents from `movies/{schedule_id}/rating_history` to `movies/{metadata_id}/rating_history`.
            *   Ensure no data loss in history (Firestore document IDs in history are dates `YYYY-MM-DD`, so they should naturally merge/overwrite).

### Phase 3: Cleanup & Verification
1.  **Verification**:
    *   Verify that all `metadata_id` documents now exist.
    *   Verify that Admin V2 pages load correctly for the merged movies.
2.  **Manual Deletion List**:
    *   Generate a clear list of `schedule_id` document paths to be deleted.
    *   Provide this list to the user for manual deletion via Firebase Console (as requested).

## Verification & Testing
*   **Dry Run**: The audit/merge script must support a dry-run mode that logs actions without performing writes.
*   **Checkpoints**:
    *   [ ] Count of `movies` collection before vs after (including subcollections).
    *   [ ] Sample check: Choose a movie known to have a `schedule_id` document and verify it's merged correctly into its `metadata_id` counterpart.

## ⚡ Trigger Analysis

The incorrect `schedule_id` documents are created during the following automated workflows:

### 1. `Daily Initial Scraper` (`daily-initial-scrape.yml`)
*   **Trigger**: Daily at 01:15 WIB.
*   **Action**: `uv run python -m backend.cli movie-details --all`
*   **Mechanism**: This command reads the "latest" snapshot (generated by `post_process.py`). If a movie in that snapshot is missing its `tix_metadata_id` (Metadata ID), the CLI falls back to using `id` (Schedule ID).
*   **Result**: If `tix_metadata_id` is blank, the metadata fetch is performed using the Schedule ID, creating a ghost document in the root `movies` collection.

### 2. `Scrape Missing Movie Details` (`scrape-movie-details.yml`)
*   **Trigger**: Daily at 01:30 WIB.
*   **Action**: `uv run python -m backend.cli movie-details --from-performance --update-ratings`
*   **Mechanism**: This command scans the **V1** `movie_performance` collection. In V1, the collection is keyed by **Schedule ID**. The CLI iterates through these keys and treats them as `movie_id` for the root `movies` collection.
*   **Result**: This explicitly forces the creation of `movies/{schedule_id}` documents for every active movie in the V1 system.

### Summary of Triggers
The problem is hardcoded into the CLI's selection logic for batch operations (`--all` and `--from-performance`). As long as these workflows run without the patch, new ghost documents will be created daily.

After a meticulous code audit, the following script has been identified as the source of the incorrect `schedule_id` document creation in the `movies` collection.

### Identified Script
`backend/cli/commands/details.py` within the `run_movie_details_scrape` function.

### Mechanism of Failure
1.  **Command `movie-details --from-performance`**:
    *   This command retrieves all unique `movie_id` fields from the `movie_performance` collection (V1).
    *   In V1, the `movie_id` is actually the **TIX Schedule ID**, not the stable Metadata ID.
    *   The script then iterates through these IDs and calls `ScrapeMovieDetailsUseCase.execute(movie_ids=[schedule_id])`.
2.  **Command `movie-details --all`**:
    *   This retrieves movies from the latest snapshot using `movie_ids = [m.tix_metadata_id or m.id for m in snapshot.movies]`.
    *   If `tix_metadata_id` is missing (common during the first scrape of the day), it falls back to `m.id`, which is the **Schedule ID**.
3.  **Use Case Behavior**:
    *   The `ScrapeMovieDetailsUseCase` takes the input ID (e.g., a Schedule ID) and fetches metadata.
    *   Even if the TIX API returns the correct Metadata ID in the payload, the script has a "force" logic: `movie_details.movie_id = movie_details.movie_id or movie_id`.
    *   If the API returns a null ID (common for expired movies) or if the logic flow preserves the input ID, the `FirestoreMovieDetailsRepository` saves the document using the input ID as the Firestore Document Key.

### Is it safe to delete the script?
**No.** The script `backend/cli/commands/details.py` and the associated `ScrapeMovieDetailsUseCase` are essential for fetching movie metadata (posters, synopsis, ratings). They should not be deleted.

**Instead, they must be patched to:**
1.  Ensure that only stable Metadata IDs are passed as input.
2.  Always prioritize the Metadata ID returned by the API over the input ID.
3.  Filter out IDs that are clearly Schedule IDs when performing batch operations.

## 🛠️ Proposed Fixes (Future Task)
*   **Fix 1**: Update `run_movie_details_scrape` to use `movie_performance_v2` as the source, which correctly uses stable Metadata IDs.
*   **Fix 2**: Update `MovieDetails.from_api_response` or the use case to strictly validate that the `movie_id` being used for the document key is the actual metadata identifier.
